# Тест · Від потреби до технічного завдання. User Stories та Use Cases
Прохідний бал: 75

## Яке формулювання є потребою, а не «вимогою-рішенням»?
- Зробити кнопку «Звіт» на головному екрані
+ Швидко формувати звіт про наявність майна
- Використати базу даних PostgreSQL для звітів
- Додати меню з переліком складів частини
> Вимога відокремлює «що» від «як»; «зробити кнопку» — це вже рішення.

## Яка User Story сформульована за шаблоном правильно?
- Додати модуль автоматичного звіряння даних обліку з фактом
+ Як обліковець, хочу авто-звіряння, щоб скоротити інвентаризацію
- Система обліку має бути зручною та швидкою для всіх користувачів
- Розробник має реалізувати звіряння до завершення поточного спринту
> Шаблон «Як <роль>, я хочу <дію>, щоб <цінність>» фокусує на потребі, а не на технічній реалізації.

## Що означає літера T у критеріях якості User Story INVEST?
- Технічна
+ Тестована
- Термінова
- Трасована
> INVEST: незалежна, обговорювана, цінна, оцінювана, мала, тестована.

## У якому форматі зазвичай записують критерії прийняття User Story?
- Specific / Measurable / Time-bound
+ Given / When / Then
- Must / Should / Could / Won’t
- Responsible / Accountable / Informed
> «За наявності умови, коли дія — тоді результат». Історія без приймальних критеріїв — типова помилка.

## Як співвідносяться епік, історія та задача?
- Задачі об’єднують в історії, історії — в епік
+ Епік розбивають на історії, історії — на задачі
- Це синоніми з різних методологій
- Епік — велика історія, яку не розбивають
> Епік — велика функціональна область; ієрархія дозволяє планувати від великого до дрібного, а історії вміщуються в ітерацію.

## Чим Use Case відрізняється від User Story?
+ Use Case — покроковий сценарій з альтернативами
- Use Case пишуть розробники, а Story — командування
- Use Case не містить актора, лише кроки системи
- Між ними немає змістовної різниці
> User Story — коротке «що і навіщо»; повнота альтернативних сценаріїв Use Case визначає надійність майбутнього рішення.

## Що обов’язково закласти в ТЗ на ІКС для ЗСУ, крім функціональних вимог?
+ Вимоги ЗІ та розмежування доступу
+ Приймальні критерії й порядок випробувань
+ Права на код, умови супроводу
- Склад команди розробників підрядника
> ТЗ лише з функціональними вимогами призводить до непогодження або залежності від підрядника.

## Що дозволяє швидко оцінити вплив зміни вимоги на пов’язані вимоги, ТЗ і тести?
- Діаграма Ганта проєкту
+ Матриця трасовуваності
- Product Backlog команди
- Тижневий статус-звіт
> RTM пов’язує потребу → вимогу → елемент ТЗ → приймальний тест; жодну зміну не ухвалюють без impact assessment.
