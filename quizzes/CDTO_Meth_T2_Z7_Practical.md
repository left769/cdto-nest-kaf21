# Тест · Управління залежностями та міжвідомча інтеграція
Прохідний бал: 75

## Що відображає dependency map проєкту?
- Перелік робіт проєкту з датами початку й завершення
+ Від чого і від кого залежить кожен ключовий результат
- Розподіл бюджету проєкту між етапами й підрядниками
- Перелік ризиків з оцінкою ймовірності та впливу
> Dependency map — карта залежностей проєкту.

## До якого типу залежностей належить погодження обміну даними органом захисту інформації?
- Технічна
- Організаційна
+ Нормативна
- Ресурсна
> Погодження, реєстрація та дозволи — нормативні залежності; їх узгоджують юрслужба та орган ЗІ.

## Яка залежність потребує найпильнішого моніторингу?
- Вихідна, на яку чекає суміжний підрозділ
+ Та, що лежить на критичному шляху
- Та, що має найдовший строк виконання
- Технічна залежність від іншої ІКС
> Критичність визначається впливом на критичний шлях: така залежність блокує весь проєкт.

## Чому саме на interface points виникає більшість інтеграційних ризиків?
- Там зосереджено найбільше програмного коду
- Там працюють найменш досвідчені виконавці
+ На стиках розходяться формати й припущення сторін
- Interface points не потрапляють до плану проєкту
> На стиках систем, команд і процесів виникають несумісність форматів, різні припущення та «нічия зона» відповідальності. Ризики знижують контрактом стику, власниками з обох боків і раннім тестуванням.

## Дві системи ведуть звання військовослужбовця. Що потрібно визначити, щоб дані не розійшлися?
- Частоту резервного копіювання обох систем
+ «Джерело істини» для цього поля
- Систему з більшою кількістю користувачів
- Формат звіту для командування
> Для кожного поля визначають первинну систему, інакше дані стануть суперечливими.

## API суміжної системи не буде готове вчасно. Які дії відповідають плану дій при невиконанні?
+ Тимчасовий обмін даними файлом
+ Ескалація до власника суміжної системи
- Повна зупинка проєкту до готовності API
- Перенесення інтеграції на кінець проєкту
> План дій для критичної залежності: обхідне рішення, перепланування, ескалація, альтернативне джерело. Зупинка проєкту й пізня ескалація — типові помилки.

## Як правильно планувати надання доступів і погоджень у проєкті?
- Як фонові задачі «у робочому порядку»
+ Як окремі залежності з власниками й строками
- Починати роботи, а доступи запитувати за потреби
- Залучати орган ЗІ після завершення розробки
> Внутрішні обмеження (ЗІ, доступи, погодження) — теж залежності: їх закладають у план із власниками, запасом часу та раннім залученням органу ЗІ.

## Що з наведеного є передумовою переходу до етапу тестування?
- Виконані приймальні критерії
- Реєстрація ІКС у реєстрі
+ Готове тестове середовище й дані
- Навчання кінцевих користувачів
> Передумова — умова, без якої неможливо перейти до етапу. Для тестування це середовище, доступи, тестові дані й критерії.
