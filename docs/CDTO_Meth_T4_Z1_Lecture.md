# Організація та супроводження впровадження ІКС (СКП) у ЗСУ

*Тема 4: Впровадження ІКС та управління стейкхолдерами · Заняття 1*

## 1. Перелік заходів створення, експлуатації та вилучення ІКС у ЗСУ

### 1.1. Життєвий цикл ІКС

ІКС проходить повний життєвий цикл: задум → створення (розробка/закупівля) → впровадження → дослідна експлуатація → бойова (промислова) експлуатація → супровід → вилучення. Кожна стадія має свої заходи й нормативні контрольні точки.

### 1.2. Заходи за стадіями

| Стадія | Ключові заходи |
| --- | --- |
| Створення / модернізація | Обґрунтування; ТЗ; розробка/закупівля; вимоги ЗІ; випробування. |
| Впровадження | Розгортання; навчання; внесення до реєстру ІКС; введення в експлуатацію. |
| Експлуатація | Супровід; оновлення; моніторинг; управління доступами. |
| Вилучення | Виведення з експлуатації; архівування/міграція даних; зняття з реєстру. |

### 1.3. Нормативна основа

Заходи регулюються порядком впровадження ІКС і ведення реєстру ІКС/СКП; кожен перехід між стадіями потребує погоджень (юрслужба, орган ЗІ) і фіксації. Недотримання процедур робить експлуатацію нелегітимною.

**Типові помилки:**

- пропуск нормативних контрольних точок (реєстрація, погодження);
- ігнорування стадії вилучення (дані «зависають»);
- впровадження без урахування вимог ЗІ.

*Проміжний висновок: ІКС має повний нормативно регламентований життєвий цикл; впровадження — лише одна з його стадій.*

## 2. Етапи впровадження ІКС: планування, пілотування, тиражування, стабілізація

| Етап | Зміст |
| --- | --- |
| Планування | Дорожня карта впровадження, ролі, ресурси, ризики, критерії готовності. |
| Пілотування | Запуск в одному підрозділі; збір зворотного зв’язку; доопрацювання. |
| Тиражування | Масштабування на інші підрозділи за перевіреним сценарієм. |
| Стабілізація | Усунення проблем, вихід на стійке використання (adoption). |

Пілот — обов’язковий етап: він дешево виявляє проблеми до масового тиражування. Пропуск пілоту переносить усі помилки одразу на всі підрозділи.

**Критерії переходу між етапами:**

| Перехід | Критерій готовності |
| --- | --- |
| Планування → Пілот | Готова дорожня карта, ролі, критерії, підрозділ-пілот. |
| Пілот → Тиражування | Пілот успішний, зауваження усунені, adoption підтверджено. |
| Тиражування → Стабілізація | Розгорнуто в цільових підрозділах, налагоджено підтримку. |
| Стабілізація → Завершення | Стійке використання, ефект (outcome) досягнуто. |

**Типові помилки:**

- тиражування без пілоту («відразу всім»);
- відсутність критеріїв переходу між етапами;
- завершення на впровадженні без стабілізації.

*Проміжний висновок: впровадження йде поетапно (пілот → тиражування → стабілізація); пілот здешевлює виявлення проблем.*

## 3. Ключові ролі команди впровадження

| Роль | Відповідальність |
| --- | --- |
| Керівник впровадження (PM) | План, координація, строки, ризики, звітність. |
| BA | Відповідність рішення вимогам; доопрацювання за зворотним зв’язком. |
| Технічний фахівець | Розгортання, налаштування, інтеграція, ЗІ. |
| Відповідальний за навчання | Підготовка й навчання користувачів. |
| Product Support | Підтримка після запуску, hypercare. |
| Представник замовника | Приймання, узгодження, доступ до користувачів. |

Кожна роль має одного відповідального (accountable); розподіл фіксують матрицею RACI (Тема 1).

**Типові помилки:**

- розмиті ролі — «всі впроваджують»;
- відсутність представника замовника в команді;
- ігнорування ролі підтримки до запуску.

*Проміжний висновок: успіх впровадження залежить від чіткого розподілу ролей і відповідальності.*

## 4. Організація навчання кінцевих користувачів

### 4.1. Чому навчання критичне

Adoption (реальне використання) прямо залежить від того, чи вміють користувачі працювати із системою. Навчання — не формальність, а частина досягнення outcome.

### 4.2. Методи й форми

- очні інструктажі та практичні заняття;
- відеоінструкції та покрокові довідники;
- наставництво (досвідчений користувач допомагає новим);
- навчальне середовище (тренування без ризику для реальних даних).

### 4.3. Оцінка результатів навчання

Оцінюють не факт «навчання проведено», а результат: чи виконують користувачі операції самостійно. Показник — частка користувачів, що працюють без допомоги підтримки.

Рівні оцінки навчання (від простого до глибокого): реакція (чи сподобалось), засвоєння (чи зрозуміли), поведінка (чи застосовують у роботі), результат (чи змінилися показники процесу). Для ЦТ найважливіші два останні — реальне застосування й ефект.

**Типові помилки:**

- навчання «для звіту» без перевірки засвоєння;
- навчання після запуску, коли система вже відторгнута;
- ігнорування ротації (нових користувачів ніхто не навчає).

*Проміжний висновок: навчання — частина досягнення outcome; оцінюють його за самостійністю користувачів, а не за фактом проведення.*

## 5. Моніторинг та контроль ходу впровадження ІКС

Хід впровадження контролюють за показниками: прогрес за етапами й підрозділами, рівень adoption, кількість і характер звернень підтримки, виконання плану навчання. Контроль дозволяє вчасно виявити пробуксовку (наприклад, низький adoption у сегменті) і відреагувати.

Інструменти — статус-звіти, дашборд впровадження, регулярні синхронізації (Тема 2). Ключовий показник — не «скільки розгорнули», а «скільки реально користуються».

| Показник | Що показує |
| --- | --- |
| Прогрес розгортання, % | Скільки підрозділів охоплено (output). |
| Рівень adoption, % | Скільки реально користуються (outcome). |
| Звернення підтримки | Характер і частота проблем. |
| Виконання плану навчання | Готовність користувачів. |

**Типові помилки:**

- контроль лише за фактом розгортання (output), без adoption (outcome);
- відсутність регулярного моніторингу під час тиражування;
- ігнорування сигналів підтримки.

*Проміжний висновок: контроль впровадження вимірює реальне використання (adoption), а не лише факт розгортання.*

## 6. Release readiness: критерії готовності до дослідної та бойової експлуатації

Release readiness — перевірка готовності ІКС до запуску за чек-листом. У ЗСУ розрізняють готовність до дослідної експлуатації (пробний режим) і до бойової (промислової) експлуатації — з різними критеріями.

- **До дослідної:** пройдені випробування; готове тестове середовище; підготовлені користувачі пілоту;
- **До бойової:** усунені зауваження дослідної експлуатації; отримані погодження; ІКС внесено до реєстру; забезпечено вимоги ЗІ; готові документація й підтримка; визначено план відкату.

**Типові помилки:**

- запуск у бойову експлуатацію без завершення дослідної;
- запуск без реєстрації та погоджень;
- відсутність плану відкату.

*Проміжний висновок: release readiness захищає від передчасного запуску; для бойової експлуатації критерії суворіші, ніж для дослідної.*

## 7. Hypercare після запуску

Hypercare — період інтенсивної підтримки в перші тижні після запуску: посилена команда підтримки, швидке реагування на інциденти, щоденний збір зворотного зв’язку, оперативні виправлення. Мета — не дати негативному першому досвіду відштовхнути користувачів і закріпити adoption.

Hypercare планують заздалегідь (склад, тривалість, канали). Згортання підтримки одразу після запуску — типова причина падіння adoption.

**Типові помилки:**

- відсутність hypercare (підтримку згорнули одразу);
- hypercare без збору зворотного зв’язку;
- невизначені канали й відповідальні.

*Проміжний висновок: hypercare закріплює adoption у критичні перші тижні; його планують заздалегідь.*

## 8. Acceptance checklist та процедура приймання замовником

Приймання — формальне підтвердження замовником, що ІКС відповідає вимогам (за приймальними критеріями ТЗ і Definition of Done). Acceptance checklist робить приймання об’єктивним.

- виконані приймальні критерії та вимоги ТЗ;
- пройдені випробування; критичні дефекти усунені;
- забезпечено вимоги ЗІ; ІКС внесено до реєстру;
- готова документація; проведено навчання;
- оформлено акт приймання.

**Типові помилки:**

- приймання «на довірі» без чек-листа й критеріїв;
- приймання без перевірки вимог ЗІ;
- неоформлений акт приймання.

*Проміжний висновок: acceptance checklist і формальний акт роблять приймання об’єктивним і завершеним.*

## 9. Передача результату в підрозділ підтримки

Handover (передача) — формальний перехід від команди впровадження до команди супроводу: передача документації, знань, доступів, відкритих питань, контактів. Без якісного handover система залишається без власника підтримки й «повисає».

- експлуатаційна документація й інструкції;
- знання про відкриті питання й особливості;
- доступи та контакти відповідальних;
- визначений власник підтримки й канал звернень.

**Типові помилки:**

- передача без документації й визначеного власника;
- закриття проєкту без handover;
- втрата знань про особливості системи.

*Проміжний висновок: handover забезпечує подальший супровід; без нього результат впровадження втрачається.*

## Додаток 3. Release readiness checklist

**До дослідної експлуатації:**

- Пройдені випробування; готове середовище.
- Підготовлені користувачі пілоту.

**До бойової експлуатації:**

- Усунені зауваження дослідної експлуатації; отримані погодження.
- ІКС внесено до реєстру; забезпечено вимоги ЗІ.
- Готові документація й підтримка; визначено план відкату.

## Додаток 4. Acceptance checklist

- Виконані приймальні критерії та вимоги ТЗ.
- Пройдені випробування; критичні дефекти усунені.
- Забезпечено вимоги ЗІ; ІКС внесено до реєстру.
- Готова документація; проведено навчання.
- Оформлено акт приймання.

## Додаток 5. Чек-лист передачі в підтримку (handover)

- Передано експлуатаційну документацію та інструкції.
- Передано знання про відкриті питання й особливості.
- Передано доступи та контакти відповідальних.
- Визначено власника підтримки й канал звернень.
- Узгоджено період hypercare.

## Додаток 6. Глосарій ключових термінів

- **ІКС — **інформаційно-комунікаційна система.
- **СКП — **спеціальна контрольована послуга / складова (за чинним визначенням).
- **Реєстр ІКС — **облік інформаційно-комунікаційних систем ЗСУ.
- **Дослідна експлуатація — **пробний режим роботи ІКС перед бойовим.
- **Бойова (промислова) експлуатація — **штатний режим використання ІКС.
- **Пілотування — **запуск в одному підрозділі для перевірки.
- **Тиражування — **масштабування рішення на інші підрозділи.
- **Adoption — **рівень реального використання рішення.
- **Release readiness — **перевірка готовності до запуску.
- **Hypercare — **інтенсивна підтримка після запуску.
- **Acceptance — **приймання результату замовником.
- **Handover — **передача результату в підтримку.
