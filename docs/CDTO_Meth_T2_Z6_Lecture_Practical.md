# Бюджетне планування та фінансовий контроль проєктів ЦТ

*Тема 2: Управління проєктами у військовому середовищі · Заняття 6*

## 1. Бюджетне планування проєктів ЦТ: cost estimation, підходи до оцінки витрат

### 1.1. Поняття та склад бюджету проєкту

Бюджет проєкту — планова вартість усіх робіт і ресурсів, необхідних для досягнення цілей. Бюджет будується на основі WBS: кожен робочий пакет отримує оцінку вартості.

**Склад витрат проєкту ЦТ:**

- оплата праці команди (внутрішні ресурси);
- закупівля або розробка рішення (підрядники);
- ліцензії, інфраструктура, хостинг;
- навчання користувачів і документація;
- супровід і підтримка (після запуску);
- резерв на ризики (contingency).

### 1.2. Прямі й непрямі витрати, CAPEX / OPEX

Прямі витрати безпосередньо належать проєкту (розробка, закупівля); непрямі — розподілені (частина інфраструктури, адміністрування). Розрізняють також капітальні витрати (CAPEX — придбання активів) та операційні (OPEX — поточне утримання, підтримка). Для ЦТ важливо враховувати не лише вартість створення, а й вартість володіння (супровід роками).

### 1.3. Методи оцінки витрат (cost estimation)

| Метод | Суть | Точність / коли |
| --- | --- | --- |
| Аналогічний | Оцінка за подібними минулими проєктами. | Низька; на ранньому етапі, швидко. |
| Параметричний | Розрахунок за нормативами (вартість × кількість). | Середня; за наявності нормативів. |
| Знизу-вгору (bottom-up) | Оцінка кожного робочого пакета WBS і підсумовування. | Висока; коли WBS деталізована. |
| Триточковий | Оптимістична/песимістична/найімовірніша, зважене середнє. | Враховує невизначеність. |

### 1.4. Резерви

До бюджету закладають два типи резервів: contingency reserve (під ідентифіковані ризики, у розпорядженні керівника проєкту) і management reserve (під непередбачені події, у розпорядженні вищого рівня). Резерв — не «запас про всяк випадок», а обґрунтована частина бюджету.

### 1.5. Приклад бюджету «знизу-вгору»

Для проєкту «Система обліку майна» (умовні людино-години):

| Робочий пакет | Оцінка, год | Тип |
| --- | --- | --- |
| Вимоги і ТЗ | 80 | Прямі, праця. |
| Розробка / закупівля | 240 | CAPEX, підрядник. |
| Випробування | 60 | Прямі, праця. |
| Впровадження + інфраструктура | 120 | CAPEX/OPEX. |
| Навчання й документація | 40 | Прямі, праця. |
| Разом (без резерву) | 540 |   |
| Резерв (contingency) 12% | ≈65 | Під ризики. |
| Разом бюджет | ≈605 | + супровід (OPEX) окремо. |

Такий підхід показує, звідки складається кожна цифра, і полегшує подальший контроль по пакетах.

**Типові помилки:**

- оцінка «однією цифрою» без урахування невизначеності;
- ігнорування вартості володіння (супровід, ліцензії);
- відсутність резерву під ризики;
- бюджет «згори» без прив’язки до WBS.

*Проміжний висновок: якісний бюджет будується знизу-вгору від WBS, враховує вартість володіння й містить обґрунтовані резерви.*

## 2. Зв’язок бюджету з обсягом, строками та якістю: трикутник проєктного обмеження

### 2.1. Трикутник обмежень

Проєкт обмежений трьома взаємопов’язаними параметрами — обсяг, строки, якість, — за фіксованого бюджету/ресурсу. Зміна одного параметра неминуче впливає на інші. Бюджет є наскрізним ресурсом, що «оплачує» будь-яку зміну.

**Обсяг ↔ Строки ↔ Якість (у центрі — бюджет/ресурс).**

### 2.2. Як зміни впливають на бюджет

- збільшення обсягу за тих самих строків → потрібно більше ресурсу → зростання бюджету;
- скорочення строків (прискорення) → додаткові ресурси/понаднормові → зростання бюджету;
- підвищення якості (додаткові перевірки, аудит) → додаткові витрати.

### 2.3. Trade-off рішення

Керівник свідомо обирає, чим поступитися. Якщо бюджет фіксований, збільшення обсягу вимагає або продовження строків, або зниження якості/скорочення іншого обсягу. Приховані компроміси — джерело перевитрат і конфліктів.

*Приклад. Командування просить додати функцію (обсяг) без зміни строку й бюджету. Чесна відповідь: це можливо лише за рахунок іншої функції або якості — потрібне рішення про пріоритети.*

**Сценарії trade-off (за фіксованого бюджету):**

| Запит | Наслідок | Рішення |
| --- | --- | --- |
| Додати обсяг | Довші строки або нижча якість. | Пожертвувати іншим обсягом або продовжити строк. |
| Скоротити строк | Більше ресурсу / вища вартість. | Збільшити бюджет або зменшити обсяг. |
| Підвищити якість | Додаткові перевірки / витрати. | Виділити ресурс або скоротити обсяг. |

**Типові помилки:**

- обіцянка «і швидше, і більше, і якісніше» за тим самим бюджетом;
- зміна обсягу без перегляду бюджету;
- приховані від стейкхолдерів компроміси.

*Проміжний висновок: бюджет пов’язаний з обсягом, строками та якістю; будь-яка зміна одного параметра має фінансові наслідки.*

## 3. Планування витрат по етапах життєвого циклу ІКС та контроль відхилень (variance analysis)

### 3.1. Розподіл бюджету по фазах

Бюджет розподіляється по етапах життєвого циклу ІКС (ініціювання, вимоги/ТЗ, розробка/закупівля, випробування, впровадження, супровід). Це дозволяє контролювати витрати поетапно, а не «загальною сумою».

### 3.2. Аналіз відхилень (variance analysis)

Variance analysis — порівняння планових і фактичних показників для виявлення відхилень:

- **Cost Variance —** відхилення за вартістю (CV = освоєний обсяг − фактичні витрати): від’ємне → перевитрата;
- **Schedule Variance —** відхилення за строками (SV = освоєний обсяг − плановий обсяг): від’ємне → відставання;
- **Індекси —** індекси CPI = EV/AC та SPI = EV/PV (< 1 → проблема).

### 3.3. Приклад розрахунку

| Показник | Значення | Тлумачення |
| --- | --- | --- |
| Плановий обсяг (PV) | 50 | Мали виконати на 50. |
| Освоєний обсяг (EV) | 45 | Виконано на 45. |
| Фактичні витрати (AC) | 55 | Витрачено 55. |
| CV = EV − AC | −10 | Перевитрата. |
| CPI = EV / AC | 0,82 | < 1 → перевитрата бюджету. |

### 3.4. Реагування на відхилення

Виявивши відхилення, керівник аналізує причину й реагує: перерозподіл ресурсу, перегляд обсягу (за погодженням), використання резерву, ескалація. Головне — реагувати рано (variance analysis дає ранній сигнал), а не за фактом вичерпання бюджету.

### 3.5. Прогноз до завершення (EAC)

На основі поточного CPI можна прогнозувати підсумкову вартість проєкту: EAC (Estimate at Completion) ≈ загальний бюджет / CPI. Якщо CPI < 1, прогнозна вартість перевищить бюджет — це ранній сигнал про потребу коригувальних дій або додаткового фінансування.

*Приклад. Бюджет 605 год, CPI 0,82 → прогноз EAC ≈ 738 год. Тобто за поточної ефективності буде перевитрата ≈130 год. Сигнал отримано завчасно — час діяти.*

**Типові помилки:**

- контроль «загальною сумою» без розбивки по фазах;
- виявлення перевитрати лише наприкінці;
- реакція без аналізу причини відхилення.

*Проміжний висновок: variance analysis дає ранні сигнали відхилень за вартістю й строками, поки їх ще можна виправити.*

## 4. Зміна бюджету при зміні обсягу: change request process та фінансові наслідки

### 4.1. Зв’язок зміни обсягу й бюджету

Будь-яка зміна обсягу (нова функція, додаткова вимога) має фінансові наслідки. Неконтрольоване розширення обсягу (scope creep) — головна причина перевитрат. Тому зміни проводять через формальний процес.

### 4.2. Процес change request

1. Ініціювання запиту на зміну (хто, що, навіщо).
2. Оцінка впливу: на обсяг, строки, бюджет, ризики, якість.
3. Рішення (погодити / відхилити / відкласти) — уповноваженою особою/радою.
4. Оновлення бюджету, плану й документів у разі погодження; запис у change log.

### 4.3. Хто ухвалює рішення

Дрібні зміни в межах повноважень і резерву ухвалює керівник проєкту; суттєві (перевищення порогу бюджету/строків) — вищий рівень (change control board / командування). Пороги визначаються заздалегідь.

*Приклад. Запит додати модуль звітності: оцінка — +15% бюджету, +3 тижні. Рішення командування: погодити з продовженням строку АБО відкласти на наступний етап. Без оцінки впливу таке рішення ухвалювати не можна.*

**Типові помилки:**

- зміна обсягу «на словах» без оцінки впливу на бюджет;
- відсутність порогів повноважень щодо змін;
- незафіксовані зміни (немає change log).

*Проміжний висновок: зміни обсягу проводять через формальний change request з оцінкою фінансового впливу — це захист від scope creep і перевитрат.*

## 5. Закупівельні обмеження у держсекторі: процедури, строки, залежність від delivery

### 5.1. Процедури закупівель

Закупівлі в держсекторі регулюються законодавством (зокрема Законом «Про публічні закупівлі») і передбачають процедури різної тривалості й формалізму залежно від суми та умов (спрощені закупівлі, тендерні процедури, закупівлі в умовах воєнного стану з особливостями).

| Тип процедури | Коли застосовна | Вплив на строки |
| --- | --- | --- |
| Пряма / спрощена | Малі суми або особливі умови. | Коротші строки. |
| Тендерна (відкриті торги) | Суми понад поріг. | Триваліші строки, формалізм. |
| Особливості воєнного стану | Визначені законодавством випадки. | Пришвидшені, але з обмеженнями. |

*Точні пороги, процедури та строки викладач звіряє з чинною редакцією законодавства про публічні закупівлі.*

### 5.2. Вплив на delivery

Закупівельні процедури часто стають вузьким місцем проєкту: їх тривалість і формалізм затримують старт розробки чи придбання. Delivery проєкту прямо залежить від строків закупівлі, які слабко піддаються прискоренню.

### 5.3. Планування з урахуванням закупівель

- закладати реальні строки закупівельних процедур у план (віхи закупівлі);
- починати закупівельні дії завчасно, паралельно з іншими роботами;
- готувати якісне ТЗ для закупівлі заздалегідь (від нього залежить і строк, і результат);
- залучати закупівельного експерта на етапі планування.

### 5.4. Формування ТЗ для закупівлі

ТЗ для закупівлі ІКС/ІТ-послуг має бути однозначним і повним: чіткі функціональні й нефункціональні вимоги (у т.ч. ЗІ, права на код, SLA, гарантії), приймальні критерії. Нечітке ТЗ призводить до закупівлі «не того» або до оскаржень і затримок (детально — у СРС).

**Типові помилки:**

- планування без урахування строків закупівель;
- пізній старт закупівельних дій;
- нечітке ТЗ → затримки, оскарження, «не те» рішення.

*Проміжний висновок: закупівлі — часте вузьке місце; їх планують завчасно, із запасом часу та якісним ТЗ.*

## 6. Практична вправа: розробка бюджетного плану та аналіз відхилень

**Мета вправи:** для типового проєкту ЦТ слухачі розробляють бюджетний план (за WBS, по фазах, з резервом) і проводять аналіз відхилень за наданими фактичними даними.

**Вихідні дані:** WBS проєкту (із Заняття 2 або новий кейс); шаблони (Додатки 1–2); умовні фактичні витрати для variance analysis.

**Форма роботи:** у парах, з подальшою взаємною перевіркою та презентацією 2–3 робіт.

### Порядок виконання

1. Скласти бюджет по робочих пакетах WBS (метод знизу-вгору) — 30 хв.
2. Розподілити бюджет по фазах ЖЦ і додати резерв (contingency) — 20 хв.
3. За наданими фактичними даними обчислити CV, CPI, SPI; зробити висновок про відхилення — 30 хв.
4. Запропонувати заходи реагування на виявлені відхилення — 15 хв.
5. Взаємна перевірка та презентація 2–3 робіт із розбором — 15 хв.

### Еталонне проходження (зразок для викладача)

**Бюджет.** Робочі пакети: ТЗ (люди), розробка/закупівля (підрядник), випробування (люди), впровадження (люди + інфраструктура), навчання (люди), супровід (OPEX). Разом + резерв 10–15%.

**Розподіл по фазах.** Основна частка — на розробку/закупівлю та впровадження; окремо — вартість володіння (супровід).

**Variance.** За даними EV=45, AC=55, PV=50: CV=−10 (перевитрата), CPI=0,82, SPI=0,9. Висновок — проєкт відстає й перевитрачає. Реагування: аналіз причини (напр., доопрацювання через нечітке ТЗ), використання резерву, перегляд обсягу, ескалація.

### Методичні вказівки викладачу

Викладач перевіряє: (1) бюджет побудований від WBS, а не «згори»; (2) враховано вартість володіння й резерв; (3) правильно обчислені CV/CPI/SPI; (4) заходи реагування конкретні. Для розбору обирає один сильний і один проблемний бюджет.

| Правильний аналіз відхилень (CV/CPI/SPI) | 0–3 | Коректні розрахунки й висновок. |
| Конкретні заходи реагування | 0–2 | Не загальні фрази. |
| Разом | 0–10 | 9–10 «відмінно»; 7–8 «добре»; 5–6 «задовільно». |

## Додаток 5. Чек-лист ТЗ для закупівлі ІКС/ІТ-послуг (для СРС)

- Чіткі функціональні вимоги (що система робить).
- Нефункціональні вимоги: захист інформації, продуктивність, доступність.
- Права на вихідний код і документацію (або ескроу).
- Вимоги SLA на підтримку та гарантії.
- Приймальні критерії (як приймаємо результат).
- Умови сумісності з наявними системами.

## Додаток 6. Глосарій ключових термінів

- **Бюджет проєкту — **планова вартість усіх робіт і ресурсів проєкту.
- **Cost estimation — **оцінка витрат проєкту.
- **Bottom-up — **оцінка вартості кожного пакета WBS із підсумовуванням.
- **CAPEX / OPEX — **капітальні витрати (придбання) / операційні (утримання).
- **Contingency reserve — **резерв під ідентифіковані ризики.
- **Трикутник обмежень — **взаємозв’язок обсягу, строків і якості за фіксованого бюджету.
- **Variance analysis — **аналіз відхилень плану від факту.
- **CV / CPI — **відхилення / індекс виконання бюджету.
- **SPI — **індекс виконання строків.
- **Change request — **формальний запит на зміну обсягу з оцінкою впливу.
- **Scope creep — **неконтрольоване розширення обсягу.

## Додаток 7. Повний приклад фінансового контролю (розбір)

Проєкт «Система обліку майна», середина реалізації. Бюджет — 605 год.

| Крок | Результат |
| --- | --- |
| 1. Зібрати дані | PV=300, EV=270, AC=330 (год). |
| 2. Обчислити відхилення | CV = 270−330 = −60 (перевитрата); SV = 270−300 = −30 (відставання). |
| 3. Обчислити індекси | CPI = 270/330 = 0,82; SPI = 270/300 = 0,90. |
| 4. Прогноз (EAC) | 605 / 0,82 ≈ 738 год → перевитрата ≈130 год. |
| 5. Причина | Доопрацювання через неповне ТЗ. |
| 6. Рішення | Використати резерв; уточнити ТЗ; за потреби — ескалація й перегляд обсягу. |

*Приклад показує повний цикл: дані → відхилення → індекси → прогноз → причина → рішення. Саме так фінансовий контроль перетворюється на управлінську дію, а не констатацію.*
