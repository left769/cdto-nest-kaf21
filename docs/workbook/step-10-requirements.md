## Підказки

| Розділ | Як заповнити | Типова помилка |
| --- | --- | --- |
| Ролі | Візьміть ролі з доріжок BPMN-моделі TO-BE (крок 8). Для кожної — що можна і чого не можна. | Одна роль «користувач», яка може все. |
| User Stories | Роль + дія + цінність. Кожна історія — одна потреба, яка вміщується в ітерацію (INVEST). | «Система має бути зручною» — немає ролі, дії й перевірки. |
| Критерії прийняття | Given / When / Then. Обов’язково додайте хоча б один критерій на **помилку або виняток**. | Лише «щасливий шлях» — ШІ не знатиме, що робити з неправильними даними. |
| Use Cases | 1–2 найважливіші сценарії з альтернативними гілками (розбіжність, відсутні дані, недоступність). | Немає альтернативних сценаріїв. |
| Бізнес-правила | Формат «якщо … то …», з конкретними значеннями (строки, пороги). | Правило, «зашите» в історію, без окремого ID — його важко перевірити. |
| Модель даних | Сутності — іменники вашого процесу. Для кожного поля: тип, обов’язковість, допустимі значення. | Відсутня модель — ШІ вигадає поля сам. |
| Нефункціональні вимоги | Мова, ролі, тестові дані, вимоги безпеки й швидкодії — конкретно, з числами. | Вимоги без чисел («швидко», «надійно»). |
| Трасовуваність | Кожен критерій успіху зі статуту → хоча б одна вимога → тест. Кожна Must-історія → тест. | Вимоги без джерела або потреби, не покриті жодною вимогою. |

## Зразок: облік майна

??? example "Розгорнути зразок (фрагмент)"

    **Ролі**

    | Роль | Що може робити | Чого не може |
    | --- | --- | --- |
    | Відповідальний за облік | Вносити й редагувати майно, проводити інвентаризацію, формувати акт | Затверджувати акт |
    | Командир | Переглядати реєстр і зведення, затверджувати акт | Редагувати майно |

    **US-01. Внесення позиції майна** — Must

    Як відповідальний за облік я хочу вносити позицію майна, щоб усе майно було в єдиному реєстрі.

    1. Given заповнені всі обов’язкові поля When натискаю «Зберегти» Then позиція з’являється в реєстрі.
    2. Given інвентарний номер уже існує When натискаю «Зберегти» Then система не зберігає позицію й показує «Інвентарний номер уже використано».

    **US-02. Інвентаризація з авто-звірянням** — Must

    Як відповідальний за облік я хочу вносити фактичну кількість і бачити розбіжності автоматично, щоб інвентаризація тривала не довше дня.

    1. Given інвентаризацію створено When вношу фактичну кількість Then система одразу позначає рядки, де факт ≠ облік.
    2. Given по позиції не внесено факт When завершую інвентаризацію Then система не дає завершити й показує список незвірених позицій.

    **US-03. Акт розбіжностей** — Must · **US-04. Затвердження акта командиром** — Must · **US-05. Зведення для командира** — Should · **US-06. Пошук і фільтр** — Should · **US-07. Експорт у CSV** — Could

    **Бізнес-правила**

    | ID | Правило |
    | --- | --- |
    | BR-01 | Інвентарний номер унікальний у межах частини. |
    | BR-02 | Якщо фактична кількість ≠ облікової, то рядок — розбіжність і потрапляє в акт. |
    | BR-03 | Якщо позицію не звіряли понад 12 місяців, то вона позначається для позачергової інвентаризації. |
    | BR-04 | Затвердити акт може лише командир. |

    **Модель даних (фрагмент): Позиція майна**

    | Поле | Тип | Обов'язкове | Примітка |
    | --- | --- | --- | --- |
    | Інвентарний номер | текст | так | унікальний (BR-01) |
    | Найменування | текст | так | |
    | Категорія | вибір зі списку | так | озброєння, засоби зв’язку, речове, інше |
    | Кількість за обліком | число | так | ≥ 0 |
    | Місце зберігання | текст | так | |
    | МВО | текст | так | вигадане ім’я |
    | Дата останньої звірки | дата | ні | для BR-03 |

    Інші сутності: Інвентаризація, Рядок інвентаризації (облік / факт), Акт розбіжностей.

    **Трасовуваність (фрагмент)**

    | Бізнес-потреба | Вимога | ID | Приймальний тест |
    | --- | --- | --- | --- |
    | Інвентаризація ≤ 1 дня | Авто-звіряння | US-02 | US-02, критерії 1–2 |
    | Розбіжності ≤ 3% | Акт розбіжностей | US-03, BR-02 | US-03, критерій 1 |
    | Дані довірені командиру | Затвердження акта | US-04, BR-04 | US-04, критерії 1–2 |

## Чек-лист самоперевірки

- Кожна роль має «що може» і «чого не може».
- 5–8 Must-історій, кожна з роллю, дією, цінністю.
- У кожної Must-історії є щонайменше 2 критерії Given/When/Then, один з них — на помилку чи виняток.
- Use Case має альтернативні сценарії.
- Бізнес-правила мають ID і конкретні значення.
- Модель даних описує всі сутності, згадані в історіях.
- Нефункціональні вимоги містять числа.
- Кожен критерій успіху зі статуту трасується до вимоги й тесту.

!!! tip "Що з цього візьме ШІ на кроці 16"
    Майже все. Ролі стануть правами в інтерфейсі, модель даних — полями форм, бізнес-правила — перевірками, а критерії Given/When/Then — вашим планом приймання. Найчастіша причина слабкого прототипу — відсутні критерії на помилки: тоді ШІ мовчки приймає будь-які дані.
