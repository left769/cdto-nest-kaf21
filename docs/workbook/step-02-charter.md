## Навіщо

Статут — «точка істини» проєкту: що саме робимо, навіщо, як зрозуміємо, що вдалося, і чого **не** робимо. WBS, Гант і roadmap перетворюють статут на план. Усі наступні кроки спиратимуться на цей документ.

**На вході:** обраний кейс ([Легенда та кейси](cases.md)), OKR проєкту з кроку 1.

## Підказки

| Поле | Як заповнити | Типова помилка |
| --- | --- | --- |
| Проблема | Опишіть біль цифрами поточного стану: скільки часу, скільки помилок, хто страждає. Цифри вигадайте правдоподібно й позначте як припущення. | «Процес неефективний» — без жодної цифри. |
| Мета | Формулюйте як зміну для людей: «частина веде облік без паперу». | «Розробити систему» — це output, а не outcome. |
| Критерії успіху | Кожен критерій: метрика + база + ціль. Візьміть Key Results з кроку 1. | Критерій, який неможливо виміряти («зручно», «швидко»). |
| Поза межами | Назвіть 2–3 речі, які зацікавлені сторони могли б очікувати, але їх не буде. | Порожнє поле — найчастіша причина «розповзання» обсягу. |
| WBS | Декомпозиція за результатами, правило 100%: усі роботи проєкту, нічого зайвого. | Пакети-дії («зробити», «налаштувати») замість результатів. |
| Гант | Вкажіть залежності й нормативні віхи (погодження ТЗ, дослідна експлуатація, реєстрація ІКС). | Список робіт із датами без залежностей — критичний шлях не видно. |
| Roadmap | Мовою результату для командування, по етапах. | Технічні задачі замість того, що отримає користувач. |

## Зразок: облік майна

??? example "Розгорнути зразок (не копіюйте — у вашому кейсі все буде інакше)"

    **Статут**

    | Розділ | Зміст |
    | --- | --- |
    | Назва проєкту | Електронний облік майна частини |
    | Проблема | Облік у 3 паперових журналах, інвентаризація триває 3 дні, розбіжності «облік/факт» — близько 8% позицій *(припущення)*. |
    | Мета (outcome) | Частина веде облік майна без паперу, дані актуальні й довірені командиру. |
    | Критерії успіху | Інвентаризація: 3 дні → ≤ 1 дня; позицій у системі: 0% → ≥ 95%; розбіжності: 8% → ≤ 3%. |
    | У межах проєкту | Реєстр майна, інвентаризація з авто-звірянням, акт розбіжностей, зведення для командира. |
    | Поза межами | Інтеграція з фінансовою системою; облік пально-мастильних матеріалів; мобільний застосунок. |
    | Стейкхолдери | Відповідальний за облік і МВО (користувачі), командир (замовник ефекту), орган ЗІ та юрслужба (погодження). |
    | Керівник проєкту | PM підрозділу ЦТ: планування, координація, ескалація до DT Lead. |
    | Строки й ресурси | ≈ 3 місяці; команда ЦТ з 4 осіб, представник служби тилу. |
    | Ключові ризики й залежності | Затримка погодження ТЗ органом ЗІ; доступність МВО для навчання; якість первинних даних. |

    **WBS (фрагмент):** 2. Вимоги і ТЗ → збір вимог; розробка ТЗ; закладення вимог ЗІ; погодження ТЗ.

    **Гант:** ТЗ (5 дн) → погодження (10 дн) → розробка (20 дн) → дослідна експлуатація (10 дн) → реєстрація (5 дн) → впровадження (15 дн). Критичний шлях ≈ 65 дн. Навчання готується паралельно й шлях не подовжує.

    **Roadmap:** I квартал — ТЗ і погодження; II — пілот в одному підрозділі; III — облік у всій частині.

## Чек-лист самоперевірки

- Проблема описана цифрами, а припущення позначені як припущення.
- Мета — це зміна для людей (outcome), а не перелік робіт.
- Кожен критерій успіху має метрику, базове й цільове значення.
- Розділ «Поза межами» містить щонайменше 2 пункти.
- WBS охоплює всі роботи (правило 100%) і побудована за результатами.
- У Ганті є залежності, нормативні віхи й визначено критичний шлях.
- Roadmap написано мовою результату для командування.

!!! tip "Що з цього візьме ШІ на кроці 16"
    Розділи «У межах проєкту» та «Поза межами» підкажуть ШІ, які функції будувати, а які — ні. Без «Поза межами» ШІ охоче додасть зайве, а прототип вийде більшим і менш точним.
