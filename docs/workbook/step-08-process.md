## Навіщо

Перш ніж змінювати процес, його треба побачити таким, яким він є. BPMN-модель показує, хто що робить, де розгалуження і де губиться час, а бізнес-правила виносять логіку рішень окремо від схеми.

**На вході:** кейс і легенда; статут (крок 2). Дані про процес, яких бракує, вигадайте правдоподібно й позначте як припущення.

**Інструмент для діаграми:** будь-який редактор BPMN, наприклад diagrams.net (draw.io) — є й офлайн-версія. Можна намалювати на папері й сфотографувати. Діаграму збережіть як `08-protses.png` поруч із файлом.

## Шаблон

```markdown title="08-protses.md"
# Процес «[назва]»: модель AS-IS

![BPMN-модель AS-IS](08-protses.png)

## 1. Межі процесу

- **Стартова подія:** [що запускає процес]
- **Кінцева подія:** [чим процес закінчується]
- **Учасники (доріжки):** [ролі]

## 2. Текстовий опис моделі

| № | Учасник | Елемент (подія / дія / шлюз) | Дані на вході / виході | Час, проблема |
| --- | --- | --- | --- | --- |
| 1 | | | | |

## 3. Бізнес-правила

| ID | Правило (якщо … то …) | Де застосовується (крок №) |
| --- | --- | --- |
| BR-01 | | |
```

## Підказки

| Поле | Як заповнити | Типова помилка |
| --- | --- | --- |
| Межі | Одна стартова й одна (або кілька) кінцевих подій. | Процес без початку чи кінця. |
| Доріжки | Окрема доріжка для кожної ролі, зокрема для командира. | Усі дії в одній доріжці — не видно передач. |
| Шлюзи | На кожному розгалуженні — підписана умова; кожне розгалуження має об’єднання. | Ромб без умов на гілках. |
| Текстовий опис | Дублює схему таблицею — його прочитає ШІ на кроці 16. | Опис, що не збігається з діаграмою. |
| Бізнес-правила | Логіку рішень винесіть з діаграми в правила з ID і конкретними значеннями. | Складна логіка «зашита» в схему. |

## Зразок: облік майна

??? example "Розгорнути зразок (AS-IS)"

    **Межі:** старт — настав строк інвентаризації (таймер); кінець — облік актуалізовано. Учасники: командир, комісія, відповідальний за облік.

    | № | Учасник | Елемент | Дані | Час, проблема |
    | --- | --- | --- | --- | --- |
    | 1 | — | Старт: настав строк інвентаризації | | |
    | 2 | Командир | Призначити комісію | Наказ | 1 день |
    | 3 | Комісія | Перерахувати майно, записати на папір | Рукописний опис | 1 день |
    | 4 | Відповідальний | Звірити опис із трьома журналами | Журнали | 1 день, ручна робота, помилки |
    | 5 | Відповідальний | Шлюз «Є розбіжності?» | | |
    | 6 | Відповідальний | Так: скласти акт розбіжностей уручну | Акт | |
    | 7 | Командир | Розглянути й затвердити акт | Акт | Очікування підпису |
    | 8 | Відповідальний | Ні: підтвердити дані в журналах | | |
    | 9 | — | Кінець: облік актуалізовано | | |

    | ID | Правило | Крок |
    | --- | --- | --- |
    | BR-01 | Інвентарний номер унікальний у межах частини. | 3–4 |
    | BR-02 | Якщо фактична кількість ≠ облікової, то позиція — розбіжність. | 5 |
    | BR-03 | Якщо позицію не звіряли понад 12 місяців, то вона підлягає позачерговій інвентаризації. | 1 |
    | BR-04 | Затвердити акт може лише командир. | 7 |

## Чек-лист самоперевірки

- Є стартова й кінцева події; учасники рознесені по доріжках.
- На кожному шлюзі підписано умови.
- Текстовий опис збігається з діаграмою; для кроків указано дані й час.
- Бізнес-правила мають ID, формат «якщо … то …» і прив’язку до кроків.
- Модель описує процес **як є**, з обхідними шляхами, а не «як в інструкції».

!!! tip "Що з цього візьме ШІ на кроці 16"
    Бізнес-правила перейдуть у вимоги (крок 10) і стануть перевірками в прототипі. Доріжки визначать ролі й права доступу.
